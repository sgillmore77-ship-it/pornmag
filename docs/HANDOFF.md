### Conventions (keep them)

- **Every query is scoped to the publication** (`Site = { publicationId }`). Every referenced ID is checked with `assertOwned` (content.ts). Tests cover cross-tenant access.
- Admin server actions follow: `requireAdmin(permission)` → data function → `audit()` → `purge(a)` (updateTag), all wrapped in `run()` that returns `ActionResult`.
- **Cache:** public pages are ISR and tagged `site:<publicationId>`. Admin changes call `updateTag`; the cron uses `revalidateTag(tag, {expire:0})`. Per-user data (comments, the save button) loads after the page through server actions, so cached HTML is identical for everyone.
- The TipTap body must be sent to server actions as plain JSON (`JSON.parse(JSON.stringify(body))`).
- Placeholder media use `storageKey "placeholder:<hex>"` and are excluded from OG and JSON-LD.
- Slugs are unique per publication. Title-based slugs get -2, -3…; a slug the editor typed that's already taken errors.
- Modules that import `server-only` (`storage`, `admin`, `reader`, `beacon`) must be mocked in Vitest (`vi.mock("@/lib/storage", …)`).

## 9. Next: AgeVerif integration

**Why:** since 25 July 2025, Ofcom requires "highly effective age assurance" for pornographic content shown to UK users. The current click-through age gate is self-declaration and doesn't qualify. Imported tube videos are explicit, so this blocks UK launch. (Not legal advice; the owner is handling legal review.)

AgeVerif docs: https://docs.ageverif.com/. It offers three ways in:

- **Checker Script (client SDK):** needs a Public Live Key per root domain (works on subdomains).
- **OAuth2 (server-side, no client script):**
  - Authorize: `GET https://api.ageverif.com/v1/oauth2/checker` with `client_id`, `redirect_uri`, `response_type=code`, `scope=read`, `state`.
  - Token: `POST https://api.ageverif.com/v1/oauth2/token` with `grant_type=authorization_code`, `code`, `redirect_uri`. Authenticate with Basic `client_id:client_secret` or body params.
  - Resources: `GET https://api.ageverif.com/v1/oauth2/resources` with `Bearer <token>`. Returns `verified`, `uid`, `country`, `assurance_level` (STANDARD / ENHANCED / STRICT), `age_threshold`, `reused`, `expires_at`.
  - The code is valid for 10 minutes. Client ID and secret come from enabling OAuth2 on the website in the AgeVerif Webmasters Platform.
- **Portable Verifications and the External API:** see the docs.
- Verified search and AI bots are let through by AgeVerif.

**Suggested design (fits the cached-page architecture; check against current docs first):**

- **Gate at the Worker,** before cached HTML, reusing the `uk-geoblock` pattern in `src/lib/geo-block.ts`:
  - Countries in a new var `AGE_VERIFY_COUNTRIES` (start with `GB`), from `request.cf.country`.
  - Visitors without a valid signed `av_pass` cookie get a gate page with "Verify your age with AgeVerif". Open paths (login, admin, `/api`, static) stay as they are.
  - Staff keep the `geo_pass` bypass.
- **Flow routes:**
  - `/api/age/start` sets a random `state` in a short-lived HttpOnly cookie and redirects to the authorize URL.
  - `/api/age/callback` checks `state`, exchanges the code, calls resources, and requires `verified === true` and `age_threshold >= 18` (and an assurance level per legal advice).
  - On success it sets the HMAC `av_pass` cookie, expiring at `min(expires_at, 30 days)`, then redirects back to the page the visitor started on.
  - Store nothing personal. Optionally log a count for analytics.
- **Secrets:** `AGEVERIF_CLIENT_ID` and `AGEVERIF_CLIENT_SECRET` as GitHub secrets, pushed with `wrangler secret put` in the deploy job (same pattern as `RESEND_API_KEY`). The owner must paste them; Claude may not.
- **Elsewhere:** for non-UK visitors, keep the existing click-through gate (or apply AgeVerif globally if legal advice says so). Decide whether `uk-geoblock` is still needed once AgeVerif is live.
- **Tests:** state mismatch, failed token exchange, `verified: false`, threshold under 18, expired or forged cookies, open paths, staff bypass. Mock `fetch` as in `tests/video-import.test.ts`.
- **Questions for the owner:**
  - Which countries need checks (UK only, or more, e.g. EU states, US states with AV laws)?
  - Which assurance level is required?
  - Does the owner have an AgeVerif account, and what does it cost per check?

## 10. Next: putting the real domain live

The owner already owns the domain, but its name hasn't been shared yet.

1. **Cloudflare zone:**
   - Add the domain to the Cloudflare account and switch its nameservers at the registrar (owner action).
   - Once the zone is active, the API token may need **Zone → Workers Routes: Edit** (and Zone Read) for the domain.
2. **Attach to the Worker:** add to `wrangler.jsonc`:
   ```jsonc
   "routes": [
     { "pattern": "example.com", "custom_domain": true },
     { "pattern": "www.example.com", "custom_domain": true }
   ]
   ```
   Pick a canonical host and 301 the other (Cloudflare redirect rule, or a `redirects` row / proxy rule).
3. **Map the host to the publication.**
   - `findPublicationByHost` only falls back to `DEFAULT_PUBLICATION_SLUG` for localhost and `*.workers.dev`. A custom domain **needs a `publication_domains` row** (`hostname`, `is_primary=true`, `kind='custom'`) for each host, or it shows "There is no publication at this address".
   - There's no admin UI for this yet. Add one (Settings → Domains, superadmin only), or a confirm-gated workflow, or SQL in the Supabase SQL editor (owner).
4. **Auth:** it uses the request origin, so sign-in works per host. Existing sessions are per host, so staff sign in again on the new domain.
5. **SEO:** canonical URLs, sitemap and JSON-LD use `ctx.origin` (the request host), so they follow automatically. Submit the sitemap in Google Search Console. Consider `noindex` on `*.workers.dev` once the domain is live.
6. **Media:** optional custom domain for the R2 media bucket (`media.example.com`) via `NEXT_PUBLIC_MEDIA_BASE_URL`; this is a build-time var. Add a Cache Rule for long TTLs.
7. **Email:** verify the domain in Resend (SPF/DKIM DNS records) and set `EMAIL_FROM`.
8. **Then AgeVerif:** register the root domain to get keys and the OAuth redirect URI.
9. **Check:** watch the CI run; then use Chrome to load the site on the new domain, sign in, run a sitemap fetch and post a test comment.
